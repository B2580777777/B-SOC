How findings from this lab move from initial detection through to resolution. Click a card to see the remediation steps.

High FND-014

Repeated SSH auth failures from single source

192.168.1.50 sent 40+ failed logins in under 2 minutes against the Ubuntu agent.

T1110
Remediation difficulty
Caution: confirm the source isn't a misconfigured internal script before blocking — check for scheduled jobs from that host first.
  1. Confirm 192.168.1.50 is not an authorized host on this network.
  2. Block the source: sudo ufw deny from 192.168.1.50
  3. Check /var/log/auth.log for any successful login from that IP before the block.
  4. If a successful login is found, rotate the affected account's credentials immediately.
Medium FND-015

Unusual sudo cache access pattern

Sudo timestamp file accessed outside normal working hours on ubuntu-VirtualBox.

T1548
Remediation difficulty
Caution: clearing sudo cache will force re-authentication for all active sessions on the host.
  1. Check when the timestamp file was last modified: ls -la /var/lib/sudo/ts/
  2. Correlate the access time against that user's actual login session in last.
  3. If unexplained, clear the cache: sudo -k
  4. Review /etc/sudoers for overly permissive NOPASSWD entries.
Investigating 2
High FND-011

File integrity alert on /etc/passwd

Confirmed unauthorized write; tracing back to the session that triggered it.

T1485
Remediation difficulty
Caution: ensure a current backup exists before restoring — an incorrect restore can lock out valid accounts.
  1. Diff the file against the last known-good backup.
  2. Check auditd logs to find the process and user that wrote to the file.
  3. If unauthorized, restore from backup and re-run file integrity checks.
  4. Widen the FIM watch scope to catch related config files.
Low FND-012

Valid account used from unfamiliar process

Legitimate credentials, but the parent process doesn't match normal usage.

T1078
Remediation difficulty
Caution: disabling the account will interrupt any of that user's active sessions.
  1. Trace the process tree: ps -ef --forest
  2. Confirm whether the parent process matches an approved script or service.
  3. If unclear, temporarily disable the account and force a password reset.
  4. Enable extra process auditing for that account going forward.

SEP 2026

Brute force against the Ubuntu agent, detected and blocked

A Python script using paramiko attempted SSH logins against the Ubuntu agent from the Kali box, cycling through a password list against a single username. Wazuh flagged the failure pattern and its active response module blocked the source IP automatically.

T1110 · Brute Force

Setup. Kali (192.168.1.50) and the Ubuntu agent (192.168.1.10) sit on the same lab network, with the Ubuntu box running the Wazuh agent reporting back to the manager.

The attack. I wrote a short Python script using the paramiko library to open an SSH connection to the Ubuntu host and attempt a login for a fixed username, looping through a list of common passwords one at a time and logging each failure.

The detection. Wazuh's SSH ruleset correlates repeated sshd authentication failures from the same source within a short window. Once the threshold was crossed, it generated a high-severity alert and matched it against the brute force rule group.

The response. Wazuh's active response module triggered automatically, adding a firewall rule to drop traffic from 192.168.1.50 — the source was blocked before the script got far enough to try a realistic password.

What I'd change next. The password list I used was small enough that the block kicked in almost immediately. A next step is testing against a larger, more realistic wordlist to see how the alert threshold and timing hold up under a slower, more evasive attack.

About this lab

B-SOC is a self-directed project built to develop and demonstrate hands-on detection engineering skills outside of a formal SOC role.

Every alert on this site comes from a real attack run against the lab, not a simulated screenshot. The goal is to practice the full detection lifecycle: generate realistic attacker behavior, tune correlation rules, map the result to MITRE ATT&CK, and write up the reasoning the way an analyst would document it for a handoff.

Currently working through log analysis, endpoint detection, and active response configuration. Next milestones: adding Suricata for network-based detection and building a basic SOAR playbook for automated triage.
